# 创作与审稿工作流改进设计

## 背景

当前工作台已经具备后台创作任务、断线恢复、人工审稿、局部重写、候选稿、版本历史和质量评测能力，但这些能力分散在 `App.tsx`、`useWorkbench.ts` 和多个纵向堆叠的面板中。用户能够完成流程，却不容易持续判断“系统正在做什么”“当前应该处理什么”以及“某次操作会修改整章还是单个场景”。

本次改进以现有 FastAPI 和后台任务协议为基础，重组前端创作主流程。目标是让用户从启动创作到章节定稿始终处于一个明确、可恢复、可验证的工作流中。

## 目标

- 持续展示当前章节、当前阶段、执行节点和任务状态。
- 在刷新、短暂断网或切换作品后正确恢复任务状态，避免旧任务污染新作品。
- 将正文阅读、问题定位、修改范围选择和审稿决定组成一个连贯闭环。
- 明确区分整章重写、单场景重写、采用候选稿、恢复历史版本和通过定稿。
- 降低 `useWorkbench.ts` 和 `App.tsx` 的职责密度，使运行控制与审稿逻辑可以独立测试。
- 保持现有后端接口和持久化模型兼容。

## 非目标

- 不重新设计整个工作台视觉语言。
- 不改变 LangGraph 节点拓扑或小说生成算法。
- 不新增多人实时协作、正文自由编辑或自动保存正文。
- 不重写知识、规划、质量和模型设置工作区。
- 不在首轮引入 WebSocket；继续使用现有持久化任务和事件轮询接口。

## 现状与约束

- `useWorkbench.ts` 同时管理作品列表、选中作品、后台任务、审稿、版本、评测、记忆、导入导出和模型轨迹。
- `App.tsx` 根据作品状态直接编排规划、写作、审稿和完成态视图。
- `ReviewPanel` 同时承载场景选择、冲突修复、质量门、审稿决定、候选稿、版本历史和版本评测，长页面下关键操作容易离开视口。
- 后端已经持久化任务状态，并通过 `getRunJobEvents` 支持增量事件读取和重连。
- 已有组件测试覆盖基础动作，但缺少完整工作流状态转换和异常恢复测试。
- 运行时数据目录 `data/`、`memory/` 和 `output/` 不属于本次改动范围。

## 方案选择

### 采用：增量整合

保留现有页面结构、接口和组件视觉风格，先拆分状态职责，再重组写作视图。每个阶段都保持应用可运行并可独立验证。

优点：回归范围可控，可以复用现有测试和 API；若某个阶段延期，前序改进仍可交付。缺点：部分旧组件会在过渡期保留适配层。

### 不采用：一次性重写工作台

一次重写可以获得更统一的组件模型，但会同时影响规划、知识、质量和模型设置，测试和验收范围过大。

### 不采用：只调整样式

单纯移动按钮或调整布局无法解决任务恢复、状态职责混杂和操作语义不明确的问题。

## 用户流程

### 启动与运行

1. 用户进入写作视图，看到当前章节和可执行的主要动作。
2. 启动任务后，创作状态栏显示排队、运行节点、取消中或重连中状态。
3. 节点事件更新阶段、章节进度和最近完成节点，但不改变页面布局尺寸。
4. 任务到达规划审阅时跳转到规划视图；到达章节审稿时留在写作视图并进入审稿模式。
5. 任务失败或中断时保留当前作品内容，并提供明确的继续或重试动作。

### 人工审稿

1. 用户在主区域阅读当前草稿。
2. 用户从场景导航或问题列表选择一个场景；正文同步定位，并显示当前修改范围。
3. 用户输入修改意见，选择重写当前场景或切回整章重写。
4. 用户也可以比较候选稿、采用候选稿、比较历史版本或恢复版本。
5. 每次改变草稿后回到正文审阅状态，直到用户通过定稿。
6. 提交期间所有冲突操作被禁用，避免重复任务。

## 信息架构

写作视图由三个稳定区域组成：

1. **创作状态栏**：位于写作视图顶部，展示章节、阶段、运行节点、连接状态和运行控制。
2. **正文阅读区**：展示当前草稿或已定稿章节，并支持按场景定位。
3. **审稿工作区**：人工审稿时显示，内部使用“决定 / 问题 / 候选稿 / 版本”标签切换内容；主要决定操作固定在面板可见区域。

桌面端保持正文为主要宽度，审稿区为辅助宽度。窄屏按状态栏、正文、审稿区顺序纵向排列，不使用遮挡正文的浮层操作条。

## 前端架构

### `useRunJob`

负责单个作品的后台任务生命周期：

- 启动、恢复和取消任务。
- 保存当前轮询作品和任务标识。
- 消费增量事件并暴露连接状态。
- 处理退避重试、AbortController 和组件卸载。
- 忽略来自旧作品或旧任务的迟到响应。
- 在任务结束后触发作品状态刷新。

该 hook 不解释审稿内容，也不管理作品列表。

### `useReviewWorkflow`

负责当前章节的审稿交互状态：

- 当前修改范围：整章或具体场景。
- 尚未提交的反馈文本。
- 当前审稿标签页。
- 提交、采用候选稿和恢复版本期间的互斥状态。
- 草稿内容发生变化后的范围重置和正文定位请求。

反馈草稿仅在当前页面会话中按作品和章节保留，不写入后端，也不进入浏览器永久存储。`App` 持有审稿控制器，切换写作、规划、设定和质量视图时保留反馈与范围；切换作品或章节时重置。

### `useWorkbench`

继续作为页面级组合 hook，但只负责：

- 作品列表和选中作品。
- 组合 `useRunJob` 与领域操作。
- 向页面提供稳定的命令接口。

评测、记忆和导入导出逻辑暂不进一步拆分，除非为保持类型边界必须移动公共代码。

### 页面组件

- `WritingWorkspace`：承载创作状态栏、正文和审稿工作区，替代 `App.tsx` 中的写作状态分支。
- `WritingStatusBar`：统一运行、等待审稿、中断、失败和完成状态。
- `ReviewWorkspace`：管理审稿标签布局和固定决定区。
- `ReviewDecisionPanel`：只负责范围选择、反馈和提交决定。
- 现有 `ChapterReader`、`ChapterCandidatesPanel`、`VersionHistory` 和 `ChapterEvaluationPanel` 继续复用，并通过小型属性扩展接入新布局。

## 状态模型

### 服务端状态

服务端仍是以下信息的唯一事实来源：

- 作品状态和当前章节。
- 后台任务状态、节点、错误和取消请求。
- 当前草稿、场景计划、质量报告和冲突。
- 候选稿、版本和评测记录。

### 客户端瞬时状态

客户端仅持有：

- 当前写作视图标签和审稿标签。
- 选择的场景与正文定位目标。
- 未提交的反馈文本。
- 请求中的按钮和连接状态。

客户端不得通过推断把服务端任务标记为完成。轮询结束后必须刷新服务端状态。

## 任务与事件流

1. 命令调用启动接口并获得持久化 `RunJob`。
2. `useRunJob` 立即写入任务摘要并开始读取事件。
3. 事件按序列号增量应用；节点事件只更新与当前作品匹配的状态。
4. 可恢复网络错误进入 `reconnecting`，按有限退避重新请求同一序列号。
5. 后端明确返回失败、取消、中断、等待审稿或完成时停止轮询。
6. 停止轮询后重新读取作品详情和状态摘要，校正客户端状态。
7. 用户切换作品或组件卸载时取消请求；迟到事件通过作品和任务标识双重校验后丢弃。

## 审稿交互规则

- 默认修改范围为整章。
- 选择场景时同时更新范围和正文定位；用户可以显式切回整章。
- 没有反馈文本时不能提交重写。
- 通过定稿不依赖反馈文本，但必须与重写动作在视觉和语义上区分。
- 任一审稿命令从发起请求开始共享互斥状态，覆盖候选稿生成、采用、版本恢复、返修、定稿及设定治理弹窗中的正典修改；导航和标签切换不解除此状态。
- 候选稿和历史版本比较是只读操作，不改变当前范围。
- 采用候选稿或恢复版本属于草稿替换操作，完成后清空未提交反馈、清除场景高亮，并以显式顶部目标滚动和聚焦正文；不恢复替换前的场景。旧章节请求的迟到完成不得改变新章节的反馈、范围、标签或焦点。
- 过期候选稿可以查看和比较，但不能采用。
- 只读作品不显示可变更操作。

## 错误处理

- **连接中断**：保留页面内容和反馈，状态栏显示重连；有限重试后转为可手动重试状态。
- **任务失败**：显示后端错误摘要，不清空草稿或反馈；允许从检查点继续。
- **取消请求**：显示“正在停止”，直到服务端确认最终状态，避免重复取消。
- **审稿提交失败**：保留反馈和范围，按钮恢复可用，并在审稿区显示错误。
- **刷新状态失败**：保留最后一次成功内容，提供局部重新加载，不强制整页刷新。
- **旧响应**：作品或任务标识不匹配时静默丢弃。

## 可访问性与响应式

- 状态变化通过 `aria-live` 宣告，但节点高频更新使用非打断级别。
- 标签页使用正确的 `tablist`、`tab` 和 `tabpanel` 语义，仅活动标签进入 Tab 顺序；左右方向键循环切换标签，Home/End 跳至首尾。
- 场景选择使用按钮和 `aria-pressed`，不能只依赖颜色表示。
- 固定操作区在窄屏恢复为普通文档流，避免遮挡正文和软键盘。
- 所有图标按钮保留可访问名称和工具提示。
- 动态内容不得改变状态栏或主要操作按钮的稳定尺寸。

## 测试策略

### Hook 测试

- 启动任务后按序消费事件并在终态刷新作品。
- 页面加载时重连活动任务。
- 可恢复请求错误进入重连并从原序列号继续。
- 切换作品后旧任务事件不再更新界面。
- 取消任务只发送一次，并等待服务端终态。
- 审稿反馈在提交失败后保留，在草稿替换后清空。

### 组件测试

- 状态栏正确展示排队、运行、重连、取消、失败和等待审稿。
- 场景选择同步更新修改范围。
- 整章和单场景重写提交正确参数。
- 重复提交被阻止。
- 审稿标签保持候选稿、版本和评测操作可用。
- 只读状态隐藏修改动作。

### 集成验证

- 运行到人工审稿，完成单场景返修并通过定稿。
- 刷新页面后恢复活动任务和等待审稿状态。
- 候选稿采用和历史版本恢复后正文正确更新。
- 桌面和窄屏视口不存在内容遮挡或操作不可达。
- 前端测试、类型检查、构建、后端测试、Ruff 和固定评测全部通过。

## 实施顺序

1. 建立现有测试基线并补充状态流测试夹具。
2. 提取 `useRunJob`，保持界面行为不变。
3. 提取 `useReviewWorkflow` 和审稿命令互斥状态。
4. 引入 `WritingWorkspace` 与 `WritingStatusBar`。
5. 将 `ReviewPanel` 拆分为标签化 `ReviewWorkspace` 和决定面板。
6. 接入场景定位、候选稿和版本操作后的视图恢复。
7. 完成错误恢复、响应式和可访问性验证。

每一步单独提交并保持测试通过；不把功能改进和无关代码格式化混在同一提交中。

## 验收标准

- 用户不刷新整页即可完成启动、停止、恢复、审稿、返修和定稿。
- 运行时始终能看到当前任务状态和当前节点。
- 刷新或短暂断网不会丢失已持久化任务，也不会串到另一部作品。
- 审稿时能明确识别并切换整章与单场景修改范围。
- 候选稿、版本历史和质量评测不再纵向挤压主要审稿操作。
- 提交失败不会丢失用户输入的反馈。
- 现有后端接口保持兼容，运行时数据目录不被修改。
- 所有自动化检查通过，并完成桌面和窄屏的浏览器验证。
