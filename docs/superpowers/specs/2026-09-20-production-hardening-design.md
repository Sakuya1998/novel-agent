# 生产可靠性与安全加固设计

## 背景

当前 Novel Agent 已具备完整的多 Agent 创作工作流、持久化检查点、后台任务、租户隔离、模型路由、导入导出和质量评测，并由后端单元/集成测试、前端组件测试和 Docker CI 覆盖。现有实现仍有四类生产风险：加密备份的自定义请求头无法通过跨域预检；浏览器会话令牌保存在 `localStorage`；Python 构建没有实际使用已提交的锁文件；浏览器与真实模型边界缺少持续验证。

本次工作分为三个可独立验收的阶段。每个阶段完成后仓库必须保持可发布，后续阶段不能成为前序修复上线的前置条件。

## 目标

- 修复跨域加密备份导出，并用真实 CORS 预检行为防止回归。
- 让就绪检查准确区分“模型已配置”和“模型未配置”，包含数据库模型路由。
- 让本地、CI 和 Docker 使用同一份 Python 锁定依赖。
- 将浏览器认证迁移为服务端管理的安全 Cookie，避免 JavaScript 读取长期会话凭据。
- 为 Cookie 认证增加与部署形态匹配的 CSRF 防护。
- 用真实浏览器覆盖关键用户流程，并为真实模型提供可选的定期兼容性验证。

## 非目标

- 不改变 LangGraph 拓扑、Agent Prompt、小说生成算法或 Canon 数据模型。
- 不替换 SQLite、ChromaDB、FastAPI、React 或现有后台任务协议。
- 不引入 OAuth、OIDC、SSO 或第三方身份服务。
- 不要求普通 PR 或本地开发持有真实模型密钥。
- 不承诺支持任意跨站嵌入；生产工作台继续以同站部署为默认模式。
- 不在本次工作中升级所有依赖到最新版本；锁定当前已验证解算结果与安全修复所需的最小变更。

## 方案选择

### 采用：分阶段增量迁移

先修复无兼容性争议的可靠性问题，再统一依赖安装，最后迁移认证并增加浏览器 E2E。阶段之间通过现有 API 契约和自动化门禁隔离。

优点：每一步可独立发布、回滚和验证；认证改动不会阻塞 CORS 修复；依赖变化与业务行为变化分离。缺点：认证迁移期间需要短期兼容 Bearer Token。

### 不采用：一次性切换所有生产边界

一次提交同时修改 CORS、依赖、认证和 E2E 会让失败归因困难，也无法安全回滚某个独立问题。

### 不采用：仅修复已复现的 CORS

这能解决直接故障，但无法处理依赖漂移和浏览器会话安全风险，也不能建立覆盖这些边界的长期验证机制。

## 阶段一：可靠性修复

### CORS 请求头

FastAPI 的 CORS 配置显式允许 `X-Backup-Password`。允许源仍由 `FRONTEND_ORIGINS` 控制，不扩大为通配符；允许方法和凭据策略保持最小范围。

测试必须发送完整浏览器预检请求：

- `Origin` 为允许的前端来源。
- `Access-Control-Request-Method` 为 `GET`。
- `Access-Control-Request-Headers` 包含 `x-backup-password`。
- 响应为成功，并在 `access-control-allow-headers` 中包含该头。

普通跨域请求、未知来源和生产通配来源拒绝规则保持不变。

### 就绪检查

`/readyz` 的模型状态由统一的模型配置检查函数产生，而不是只检查环境变量。判断顺序为：

1. 数据库中三类模型路由完整且引用有效档案时，状态为 `configured`，来源为 `database`。
2. 没有数据库路由且环境回退配置完整时，状态为 `configured`，来源为 `environment`。
3. 两者都不完整时，状态为 `unconfigured`。

模型服务的外部连通性不进入每次就绪检查，避免健康检查产生费用、延迟或供应商依赖。`unconfigured` 只作为
`checks.model` 诊断状态返回，不影响基础设施就绪；真正执行创作或评测时仍会拒绝未配置的模型。现有
`/healthz` 继续只表示进程存活。

这样部署可以先启动工作台，再由用户完成模型配置，避免首次部署因缺少模型路由而无法进入配置界面。

## 阶段二：可复现构建

### 唯一依赖来源

`pyproject.toml` 继续声明直接依赖及兼容范围，`uv.lock` 作为应用部署与 CI 的唯一完整解算结果。`requirements.txt` 保留为面向传统 pip 用户的直接依赖清单，但不再用于 CI 和 Docker 的生产安装。

### 安装路径

- 本地推荐：`uv sync --locked --all-extras`。
- CI：安装固定版本的 uv，然后使用 `uv sync --locked --all-extras` 执行测试。
- Docker builder：复制 `pyproject.toml`、`uv.lock`、README 和源码，使用锁文件安装生产依赖，不安装 dev extra。
- 依赖审计：从锁定环境或由锁文件导出的冻结清单执行，确保审计对象与发布对象一致。

锁文件与 `pyproject.toml` 不一致时，构建必须失败，禁止自动重新解算。前端继续使用已有的 `package-lock.json` 与 `npm ci`。

### 镜像约束

运行镜像继续保留非 root 用户、只读根文件系统、最小 capabilities 和现有健康检查。构建阶段引入 uv 不能让 uv、编译缓存或开发依赖进入最终镜像。

## 阶段三：安全认证与 E2E

### Cookie 会话

登录和注册成功后，后端通过 `Set-Cookie` 写入不透明会话令牌：

- `HttpOnly`：前端 JavaScript 无法读取。
- `Secure`：生产环境强制启用；开发环境允许 HTTP localhost。
- `SameSite=Lax`：支持正常顶层导航并降低跨站请求风险。
- `Path=/`：覆盖 API 请求。
- `Max-Age` 与服务端会话到期时间一致。

前端删除 `localStorage` 中的访问令牌，只保留非敏感用户展示信息或完全以 `/api/auth/status` 为准。退出登录同时撤销服务端会话并清除 Cookie。

### Bearer 兼容窗口

为避免现有 CLI/API 客户端立即失效，认证中间件在一个明确兼容版本内同时接受：

1. 浏览器 Cookie。
2. `Authorization: Bearer`。

Cookie 优先，Bearer 用于 CLI、脚本和旧客户端。登录响应在兼容期仍可返回 `access_token`，但 React 前端不得保存或发送它。README 标记 Bearer 响应为兼容接口，并给出后续移除条件；本次不删除 Bearer 支持。

### CSRF 防护

所有使用 Cookie 身份的写请求采用双提交 Token：

- 登录/注册响应同时设置一个非 HttpOnly 的 CSRF Cookie，并在响应体返回相同 token。
- React 仅读取 CSRF token，并通过 `X-CSRF-Token` 发送到 `POST`、`PUT`、`PATCH`、`DELETE` 请求。
- 后端对 Cookie 认证的写请求比较请求头和 CSRF Cookie，使用常量时间比较。
- Bearer 认证不要求 CSRF token，因为浏览器不会自动附加 Authorization 头。
- 登录和注册继续受现有限流保护；其 CSRF token 在成功认证后生成。

CORS 仅在显式允许来源上启用凭据，并允许 `X-CSRF-Token` 与 `X-Backup-Password`。生产配置继续拒绝通配来源。

### 会话迁移

首次加载时，React 调用 `/api/auth/status`：

- 有有效 Cookie 时恢复用户。
- 只有旧 `localStorage` Token 时，兼容版本可用 Bearer 调用一次状态接口；成功后前端要求重新登录以获得 Cookie，不自动把 Bearer 转换为 Cookie。
- 无有效身份时清除旧浏览器数据并显示登录界面。

不增加隐式 Token 交换端点，避免延长旧凭据生命周期。

## 浏览器 E2E

### 工具与环境

使用 Playwright 启动真实 FastAPI 和 Vite/生产预览服务。测试使用隔离的临时 SQLite、checkpoint、Chroma 和密钥目录，不读取或修改开发者的 `memory/`、`data/` 和 `output/`。

普通 PR E2E 使用确定性假模型或测试专用模型适配器，不访问外部网络。覆盖：

- 注册、登录、刷新恢复和退出。
- 创建作品并启动后台任务。
- 刷新后恢复活动任务或人工审查状态。
- 提交审查操作并观察状态推进。
- 跨域加密备份导出及下载。
- Viewer 写操作被拒绝。
- Cookie 写请求缺少或伪造 CSRF token 时被拒绝。

桌面和移动视口至少各运行一条核心流程，并检查浏览器控制台无未处理错误。

### 真实模型验证

真实模型测试作为独立 nightly 或手动工作流运行：

- 仅在所需密钥存在时启用。
- 使用最小章节数和严格 token 预算。
- 验证模型连接、结构化输出解析、一次完整章节流程和错误脱敏。
- 不把生成文本快照作为稳定断言；断言结构、状态转换和安全属性。
- 失败不在普通 PR 中阻塞无密钥贡献者，但必须产生可见报告。

## 错误处理与回滚

- CORS 或就绪检查改动失败时，只回滚阶段一，不影响认证和依赖。
- 锁文件安装失败时保留原发布镜像，禁止 CI 临时放宽 `--locked`。
- Cookie 认证出现问题时，可在兼容期继续使用 Bearer 客户端；React 回滚到上一版本不会破坏服务端会话表。
- CSRF 校验失败统一返回 403，不在响应或日志中输出 token。
- E2E 临时服务异常退出时必须清理进程和临时目录，不触碰持久开发数据。

## 测试策略

### 阶段一

- CORS 自定义头预检先失败、修复后通过。
- 数据库路由、环境回退和无配置三种就绪状态。
- 全量后端测试、Ruff、前端测试、类型检查、构建和固定评测。

### 阶段二

- `uv sync --locked` 在干净环境成功。
- 修改依赖声明但不更新锁文件时，锁定安装失败。
- Docker 构建与 Compose smoke test 成功。
- 审计运行于锁定依赖集合。

### 阶段三

- Cookie 属性、登录恢复、退出清除和过期会话。
- Cookie 与 Bearer 双通道优先级和租户隔离。
- Cookie 写请求的 CSRF 成功、缺失、错误和只读方法场景。
- 前端不再读写访问令牌。
- Playwright 核心流程和跨域下载。
- 可选真实模型工作流的结构化报告。

所有行为变更遵循测试先行：先建立能证明缺陷或缺失行为的失败测试，再做最小实现。

## 实施顺序

1. 阶段一：新增 CORS 和就绪检查失败测试，完成最小修复并运行全量门禁。
2. 阶段二：切换本地说明、CI、Docker 和依赖审计到锁文件，完成干净环境与镜像验证。
3. 阶段三 A：后端 Cookie、Bearer 兼容与 CSRF，完成 API 测试。
4. 阶段三 B：React 会话迁移和前端测试。
5. 阶段三 C：Playwright 确定性 E2E。
6. 阶段三 D：可选真实模型 nightly 工作流与文档。

每个阶段独立提交；不得把自动格式化、依赖升级或无关重构混入功能提交。

## 验收标准

- 允许来源的加密备份跨域预检成功，未知来源仍不能读取响应。
- `/readyz` 能识别数据库模型路由，未配置模型时不再报告模糊的 `fallback`。
- CI 和 Docker 严格使用 `uv.lock`，锁文件漂移会导致构建失败。
- React 不在 Web Storage 中保存会话令牌，也不主动发送 Bearer Token。
- 生产会话 Cookie 具有 `HttpOnly`、`Secure` 和 `SameSite=Lax`。
- Cookie 认证的写请求必须通过 CSRF 校验，Bearer 客户端保持兼容。
- Playwright 在真实浏览器中完成关键工作流，且不访问开发数据目录。
- 普通 PR 不依赖外部模型密钥；真实模型工作流可独立运行并产生结果。
- 后端、前端、质量评测、部署检查、依赖审计和容器烟测全部通过。
