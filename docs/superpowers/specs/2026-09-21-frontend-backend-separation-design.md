# 前后端分离与团队工作区产品化设计

## 1. 背景与目标

当前仓库同时包含 FastAPI 后端和 React 单页工作台。单页入口把认证、工作区、作品列表、写作流程、模型设置、监控和导入导出集中在一个应用状态树中，导致页面边界、权限边界和发布边界互相耦合。

本设计的目标是：

1. 将前端迁移为独立仓库和独立发布物。
2. 保留现有写作、规划、知识、质量、评测、模型路由和异步任务能力。
3. 把当前 \`tenant_id\` 演进为明确的团队工作区语义，固化 \`owner/editor/viewer\` 权限。
4. 将内容类型、风格、创作约束模板、质量策略变成可版本化的工作区资源。
5. 通过 API 版本化、OpenAPI 契约和兼容窗口支持渐进迁移、灰度发布和回滚。

非目标：第一阶段不更换 Agent 编排框架、不把 SQLite 强制替换为 PostgreSQL、不开放任意工作流节点配置、不把角色/世界观等作品 Canon 变成工作区共享资源。

## 2. 领域模型

### 2.1 身份与边界

- \`user\`：登录身份和个人资料。
- \`workspace\`：团队协作边界。第一阶段复用现有 \`tenant_id\` 作为持久化标识，API 和前端统一称为 workspace。
- \`membership\`：用户在工作区中的关系，角色为 \`owner\`、\`editor\` 或 \`viewer\`。
- \`novel\`：归属于一个工作区的作品；作品下包含规划、章节、Canon、评测和任务。
- \`resource\`：工作区可管理的配置资源，分为 content type、style、creative template、quality policy 四类。
- \`resource_version\`：已发布资源的不可变版本。
- \`job\`：异步生成、修订、评测、导入导出任务。
- \`audit_event\`：身份、权限、资源和作品治理动作的审计事件。

### 2.2 资源分类

首期资源中心包含：

| 资源 | 用途 | 首期规则 |
| --- | --- | --- |
| 内容类型 | 作品题材/分类 | 支持父子层级、别名、标签和启停 |
| 风格 | 生成和润色风格 | 系统内置不可删除；工作区可复制、编辑、发布 |
| 创作约束模板 | 读者、视角、时态、距离、结局、主题、强度等 | 保存完整 CreativeBrief，不拆成独立枚举资源 |
| 质量策略 | 质量门槛、回归阈值等 | 评分维度和协议仍由系统控制 |

出版配置、项目模板、主题词库和叙事线程分类暂列后续版本。角色、世界观、事实和叙事线程实例始终属于作品。

### 2.3 生命周期和版本

资源状态为 \`draft\`、\`published\`、\`disabled\`，另有软删除标记。published 版本不可原地修改；编辑会创建新草稿，发布后递增版本号。停用影响新作品选择，不影响历史作品和已运行任务。

作品创建时保存资源引用；生成任务开始时保存资源 payload 的快照和版本号。任务、章节和历史作品只读取快照，不重新读取当前工作区资源。

## 3. 权限模型

| 能力 | owner | editor | viewer |
| --- | --- | --- | --- |
| 查看工作区、作品和已发布资源 | ✓ | ✓ | ✓ |
| 创建/编辑/删除作品 | ✓ | ✓ | ✗ |
| 启动、取消、恢复生成任务 | ✓ | ✓ | ✗ |
| 编辑 Canon、规划和创作约束 | ✓ | ✓ | ✗ |
| 管理内容类型、风格、模板、质量策略 | ✓ | ✗ | ✗ |
| 管理成员和角色 | ✓ | ✗ | ✗ |
| 管理模型密钥和路由 | ✓ | ✗ | ✗ |
| 查看审计日志 | ✓ | 视后续策略，首期只读 | 仅不开放 |

后端每个查询和写操作都从当前 principal 推导 workspace，并检查资源/作品归属。前端隐藏和禁用按钮只用于体验，不作为安全边界。

## 4. API 与前端边界

新契约统一使用 \`/api/v1\`：

- \`/api/v1/auth/*\`
- \`/api/v1/workspaces/*\`
- \`/api/v1/workspaces/{id}/members\`
- \`/api/v1/workspaces/{id}/resources/*\`
- \`/api/v1/novels/*\`
- \`/api/v1/jobs/*\`
- \`/api/v1/model-settings/*\`
- \`/api/v1/audit/*\`

所有公开请求统一使用 \`/api/v1/*\`；迁移稳定窗口结束后旧 \`/api/*\` 已移除并返回 410 迁移提示。所有列表接口使用 \`limit\`、\`cursor\` 和 \`has_more\`。写操作支持版本冲突检查；创建和启动任务支持 \`Idempotency-Key\`。

统一错误响应：

\`\`\`json
{
  "code": "resource_version_conflict",
  "message": "资源版本已变化，请刷新后重试",
  "request_id": "req_01...",
  "details": {"expected_version": 2, "actual_version": 3}
}
\`\`\`

OpenAPI 文档由后端生成并提交为可审查 artifact；独立前端通过生成的 TypeScript 客户端消费，不引用后端源代码。

## 5. 认证与部署拓扑

生产首选同一主域的子域名：\`app.example.com\` 和 \`api.example.com\`。会话使用 Secure、HttpOnly、SameSite Cookie；跨 origin 时配置精确 CORS allowlist 和 CSRF 双提交校验。若部署环境不方便配置跨域，则由反向代理以单一 origin 提供静态前端和 \`/api/v1\`，客户端仍只依赖 \`/api/v1\` 契约。

前端构建、镜像和发布完全独立；运行时通过环境变量或注入配置得到 API 基地址。后端不再负责构建或托管前端静态文件，迁移窗口内保留旧前端镜像作为回滚目标。

## 6. 迁移与回滚

迁移顺序：

1. 增加新表/字段和 \`/api/v1\`，不删除旧字段和旧路由。
2. 为旧作品生成兼容资源快照，执行 dry-run 和校验。
3. 独立前端先只读接入，再开启创建作品和任务操作。
4. 灰度切换后端 API 流量和前端用户。
5. 稳定窗口结束后移除旧前端构建和旧 API 别名；故障恢复依赖发布系统中的镜像 tag 与已验证数据库备份。

恢复要求：保留数据库备份、已发布镜像 tag 和兼容字段；资源迁移采用加法字段和可重复执行脚本，不在灰度期间执行不可逆删除。

## 7. 验收标准

- 新前端可以独立安装、类型检查、测试、构建和发布。
- 不同工作区无法读取或修改彼此的作品、资源、任务和模型配置。
- owner/editor/viewer 的正向和反向权限测试通过。
- 作品和任务在资源被修改或停用后仍使用创建时快照。
- 新旧前端可在同一后端兼容窗口内运行，任务可在刷新/断线后恢复。
- 灰度失败可以在不丢失数据的情况下恢复旧前端和旧路由。
